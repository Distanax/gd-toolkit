# Asking for Feedback

Source: https://www.gdcreatorschool.com/docs/guides/main-skills/asking-for-feedback/ — by komatic5
(GD Creator School, Main Skills, Grade 0). Accessed 2026-10-09.

## Key rules (paraphrased)
1. **Know exactly what you need feedback on before asking.** Vague questions get vague answers
   (a "modern block" request draws guesses; "a simple block that looks like a bookshelf" gets useful
   replies).
2. **Describe the work:** what you're trying to make or learn, whether it's practice or serious, what
   inspired it, what you like and dislike about it.
3. **Receiving:** be polite, don't get defensive, explain intentions politely if needed. You don't have
   to accept every suggestion; decline politely when it doesn't fit your goals.
4. **Using feedback:** (a) list every suggestion/issue, (b) evaluate how each would change the work,
   (c) choose and revise, then go back to the same people for another round.
5. Feedback feeds new ideas, restarting the loop: idea -> plan -> execute -> opinions.
6. Where: the guide mentions the GD Discord server; RobTop's rating doc also points there and to
   in-game comments (notes/robtop-rating.md).

## Mapping to our work
- Every PLAYTEST.md request states: what is being tested, the stage (layout/structure/deco/final), the
  intent of the section, what we already think is weak, and 2-4 specific questions.
- Feedback processing is a written table in PLAYTEST.md Results: suggestion -> expected effect ->
  decision (do / don't, with reason) -> commit that applied it.
- The capstone feedback package (task 145) follows rule 2: intent, inspiration, practice vs serious,
  self-identified strengths and weaknesses.

## How to verify
- Not an editor rule. Check: each PLAYTEST.md request has specific questions; each received item has a
  recorded decision.
